# Framework Directory Layout

## Consumer Project

A Hestia project follows a strict directory layout. The CLI enforces this structure so that tooling, code generation, and migrations work consistently.

```
.
├── hestia.json                        # project config
├── go.mod
├── core/                              # shared services, always loaded
│   └── <module-name>/
│       ├── module.go
│       └── <service-name>/
│           ├── handler.go
│           └── model/
│               ├── <entity>.schema.json
│               └── migrations/
├── modules/                           # feature modules, per-command
│   └── <module-name>/
│       ├── module.go
│       └── <service-name>/
│           ├── handler.go
│           └── model/
│               ├── <entity>.schema.json
│               └── migrations/
├── cmd/
│   └── <name>/
│       └── main.go
└── internal/
    └── autogen/
```

Two module directories exist by convention:

- **`core/`** holds shared services that every command loads. These are always registered before any feature module.
- **`modules/`** holds feature modules. Each command declares which modules it uses in `hestia.json`.

## Module Structure

Every module is self-contained. Schemas, generated code, and migrations live inside the module — nothing is shared across module boundaries.

```
<module-name>/
├── module.go                         # Setup(), Capabilities()
└── <service-name>/
    ├── handler.go                    # @hestia.register annotated handlers
    ├── registrations.go              # generated
    ├── policies.go                   # generated
    ├── sanitization.go               # seed file, author-owned
    └── model/
        ├── <entity>.schema.json      # schema definition
        ├── <entity>.schema.model.go  # generated
        ├── data_transfer_objects.go  # input/output types
        └── migrations/
            ├── 001_create_<entity>.go
            └── 002_add_<field>.go
```

### `module.go` — The Entry Point

Implements the `abstract.Module` interface. The runtime calls `Setup()` during boot to register service providers, then `Capabilities()` after the container is sealed to collect message registrations.

```go
package notifications

import (
    "context"
    "github.com/asaidimu/hestia/core/abstract"
    "github.com/user/myapp/modules/notifications/alerts"
)

type Module struct{}

func (m Module) Name() string { return "notifications" }

func (m Module) Setup(ctx context.Context, rt abstract.Container) error {
    return alerts.RegisterService(rt)
}

func (m Module) Capabilities(rt abstract.Container) ([]abstract.Capability, error) {
    regs, err := alerts.Registrations(rt)
    if err != nil {
        return nil, err
    }
    return []abstract.Capability{
        {Name: "notifications", Messages: regs},
    }, nil
}
```

A module with multiple services calls each service's `RegisterService()` in `Setup()` and each `Registrations()` in `Capabilities()`.

### `handler.go` — The Author's Code

The developer writes service methods annotated with `@hestia.register`. These annotations drive code generation.

```go
package alerts

import (
    "context"
    "github.com/asaidimu/hestia/core/abstract"
    "github.com/user/myapp/modules/notifications/alerts/model"
)

type AlertsService struct{}

func NewAlertsService(rt abstract.Container) (*AlertsService, error) {
    return &AlertsService{}, nil
}

// CreateAlert creates a new notification alert.
//
// @hestia.register(
//   name="notifications:alerts:create",
//   intent="create",
//   rule="authenticated",
//   description="Create a new alert",
// )
func (s *AlertsService) CreateAlert(ctx context.Context, msg abstract.Message, input *model.CreateAlertInput) (*model.Alert, error) {
    // handler logic
}
```

Method signature is fixed: `(ctx, msg, input) -> (output, error)` or `(ctx, msg, input) -> error`.

The `@hestia.register` attributes:
- `name` — route name, pattern `<module>:<service>:<resource>:<action>`
- `intent` — CRUD intent: `create`, `read`, `update`, `delete`
- `rule` — IAM policy binding key
- `description` — human-readable description
- `resource_id` — which input field is the document ID (optional)

### `registrations.go` — Generated

Produced by `hestia service generate` from `@hestia.register` annotations. Contains `RegisterService()` and `Registrations()`.

```go
// Code generated by cmd/hestia service generate. DO NOT EDIT.

package alerts

import (
    "github.com/asaidimu/hestia/core/abstract"
    dispatch "github.com/asaidimu/hestia/core/runtime/dispatch"
    "github.com/user/myapp/modules/notifications/alerts/model"
)

func RegisterService(rt abstract.Container) error {
    return abstract.Register[*AlertsService](rt, func(c abstract.Container) (*AlertsService, error) {
        return NewAlertsService(c)
    })
}

func Registrations(rt abstract.Container) ([]abstract.MessageRegistration, error) {
    s := abstract.MustResolve[*AlertsService](rt)
    return []abstract.MessageRegistration{
        {
            Name:        "notifications:alerts:create",
            Description: "Create a new alert",
            Intent:      abstract.Create,
            Enabled:     true,
            Input:       abstract.Input{Schema: dispatch.SchemaFromTypeWithTag[model.CreateAlertInput]("input")},
            Output:      dispatch.SchemaFromType[model.Alert](),
            Handler:     dispatch.HandleDocument[model.CreateAlertInput, *model.Alert](s.CreateAlert),
        },
    }, nil
}
```

### `policies.go` — Generated

Maps each route to an IAM rule. Also produced by `hestia service generate`.

```go
// Code generated by cmd/hestia service generate. DO NOT EDIT.

package alerts

import "github.com/asaidimu/hestia/core/system/policies"

func Policies() []policies.Binding {
    return []policies.Binding{
        {Name: "notifications:alerts:create", RuleKey: "authenticated", Description: "Create a new alert"},
    }
}
```

### `sanitization.go` — Seed File

Written once by the author. Defines which fields to redact in responses. Never overwritten by code generation.

```go
package alerts

import "github.com/asaidimu/go-anansi/v8/core/sanitize"

func SanitizationRules() *sanitize.FieldMaskConfig {
    return &sanitize.FieldMaskConfig{
        DefaultPolicy: sanitize.MaskPreserve,
        Fields: map[string]sanitize.MaskedFieldPolicy{
            "secret_key": sanitize.MaskRedact,
        },
    }
}
```

### `model/` — Schema and Types

**`<entity>.schema.json`** — defines the collection shape:

```json
{
  "name": "notifications_alerts",
  "version": "1.0.0",
  "fields": {
    "title": { "type": "string", "required": true },
    "body": { "type": "string" },
    "read": { "type": "boolean", "default": false }
  },
  "indexes": [
    { "name": "by_user", "fields": ["user_id"] }
  ]
}
```

**`<entity>.schema.model.go`** — generated from the schema by go-anansi codegen. Provides `InitModel()`, CRUD methods, query helpers, and document types.

**`data_transfer_objects.go`** — input/output types for handlers:

```go
package model

type CreateAlertInput struct {
    Title string  `json:"title"`
    Body  *string `json:"body,omitempty"`
}

type Alert struct {
    ID    string  `json:"id"`
    Title string  `json:"title"`
    Body  *string `json:"body,omitempty"`
    Read  bool    `json:"read"`
}
```

### `migrations/` — Generated Migration Files

Each migration is a Go file generated by `anansi schema migrate` from schema diffs. The developer edits `.schema.json`, then runs `hestia migrate` to produce migration files.

```
model/
├── alert.schema.json               # author edits (source of truth)
├── alert.schema.model.go           # generated by codegen
├── data_transfer_objects.go        # author writes
└── migrations/
    └── <uuid>__alerts__major.go    # generated by anansi schema migrate
```

The generated migration file contains:
- UUID-based filename (e.g., `01a0476f-a2fd-74a8-83ef-b52ead1a28e8__alerts__major.go`)
- Embedded target schema as JSON
- `MigrationPlan` with `Description`, `Target`, `VersionBump`, `Transformer`
- `Transformer` has a `panic("implement transformer")` stub — author fills in only when data transformation is needed

Each module carries its own migrations — there is no centralized migration directory.

## Migration

### The `Migration` Type

Defined in `core/runtime/module`, this is the framework's wrapper around anansi's migration plan:

```go
type Migration struct {
    UUID          string
    Collection    string
    From          string
    To            string
    File          string
    Plan          func() *base.MigrationPlan
    SubMigrations []Migration
}
```

### Module Interface Extension

Modules return their migrations via a `Migrations()` method:

```go
func (m Module) Migrations() []Migration {
    return notifications.Migrations()
}
```

### Generated Command Files Aggregate Migrations

Each command's generated file returns both modules and migrations:

```go
// internal/autogen/api_modules.go
package autogen

import (
    "github.com/asaidimu/hestia/core/runtime/module"
    "github.com/user/myapp/core/tenants"
    "github.com/user/myapp/modules/notifications"
)

func ApiModules() ([]module.Module, []module.Migration) {
    mods := []module.Module{
        tenants.Module{},
        notifications.Module{},
    }
    var migrations []module.Migration
    migrations = append(migrations, tenants.Migrations()...)
    migrations = append(migrations, notifications.Migrations()...)
    return mods, migrations
}
```

### Boot-Time Application

`hestia.Setup()` receives the aggregated migrations and calls `migrations.Apply()` after all modules are set up. The `Apply` function handles:
- Creating collections from the first migration's target schema
- Applying pending migrations in order
- Detecting schema version drift

## Config (`hestia.json`)

```json
{
  "module": "github.com/user/myapp",
  "core_dir": "core",
  "modules_dir": "modules",
  "autogen": "internal/autogen",
  "commands": {
    "api": {
      "entry": "cmd/api/main.go",
      "uses": ["notifications"]
    }
  }
}
```

| Field | Default | Purpose |
|---|---|---|
| `module` | auto-detected | Go module import path |
| `core_dir` | `"core"` | Shared services directory |
| `modules_dir` | `"modules"` | Feature modules directory |
| `autogen` | `"internal/autogen"` | Generated code output |
| `commands` | `{}` | Named entry points with module dependencies |

Each command declares which feature modules it uses. Core modules are always loaded implicitly.

## Getting Started

Create a new project and initialise it in one step:

```bash
mkdir myapp && cd myapp
hestia init github.com/user/myapp
```

This produces:

```
myapp/
├── hestia.json
├── go.mod
├── go.sum
├── core/
├── modules/
├── cmd/
│   └── myapp/
│       └── main.go
└── internal/
    └── autogen/
        └── modules.go
```

`hestia init` runs `go mod init`, scaffolds the directory structure, generates the entry point and module registry, and runs `go mod tidy`. The project is ready to build.

## Adding a Command

```bash
hestia add cmd worker
```

**Creates `cmd/worker/main.go`:**

```go
package main

import (
    "os"

    hestia "github.com/asaidimu/hestia/core"
    "github.com/user/myapp/internal/autogen"
)

var version = "dev"

func main() {
    app, err := hestia.Setup(hestia.SetupConfig{
        Version:     version,
        ProjectName: "worker",
        Modules:     autogen.WorkerModules(),
    })
    if err != nil {
        panic(err)
    }
    if err := app.Start(); err != nil {
        panic(err)
    }
    defer app.Close()
    os.Stdout.Sync()
    select {}
}
```

**Updates `hestia.json`:**

```json
{
  "commands": {
    "worker": {
      "entry": "cmd/worker/main.go",
      "uses": []
    }
  }
}
```

**Generates `internal/autogen/worker_modules.go`:**

```go
package autogen

import "github.com/asaidimu/hestia/core/runtime/module"

func WorkerModules() ([]module.Module, []module.Migration) {
    return nil, nil
}
```

The generated function returns both modules and migrations. Core modules and their migrations appear first, followed by feature modules from `uses` in order.

## Adding a Module

```bash
hestia add module notifications
```

Creates a self-contained module at `modules/notifications/` with a stub handler, model directory, and migrations directory. Then regenerates every command's `XxxModules()` function to include it if listed in that command's `uses`.

To add a shared core service instead:

```bash
hestia add module tenants --core
```

Creates the module at `core/tenants/`. Core modules are loaded by every command automatically, so all `XxxModules()` functions are regenerated to include it first.

## Using a Module in a Command

```bash
hestia use api notifications workflows
```

Adds `notifications` and `workflows` to the `api` command's `uses` list in `hestia.json`. Then regenerates `api_modules.go` to include them.

```bash
hestia unuse api notifications
```

Removes `notifications` from the `api` command's `uses` list. Then regenerates `api_modules.go` to exclude it.

## Module Regeneration

When a module is added or removed, every command's `XxxModules()` function is regenerated. The function returns all modules in order: core modules first, then feature modules from that command's `uses` list.

Given this config:

```json
{
  "commands": {
    "api": { "uses": ["notifications"] },
    "worker": { "uses": ["workflows"] }
  }
}
```

And core modules `tenants` and `billing`, the generated files are:

`internal/autogen/api_modules.go`:

```go
package autogen

import (
    "github.com/asaidimu/hestia/core/runtime/module"
    "github.com/user/myapp/core/tenants"
    "github.com/user/myapp/core/billing"
    "github.com/user/myapp/modules/notifications"
)

func ApiModules() ([]module.Module, []module.Migration) {
    mods := []module.Module{
        tenants.Module{},
        billing.Module{},
        notifications.Module{},
    }
    var migrations []module.Migration
    migrations = append(migrations, tenants.Migrations()...)
    migrations = append(migrations, billing.Migrations()...)
    migrations = append(migrations, notifications.Migrations()...)
    return mods, migrations
}
```

`internal/autogen/worker_modules.go`:

```go
package autogen

import (
    "github.com/asaidimu/hestia/core/runtime/module"
    "github.com/user/myapp/core/tenants"
    "github.com/user/myapp/core/billing"
    "github.com/user/myapp/modules/workflows"
)

func WorkerModules() ([]module.Module, []module.Migration) {
    mods := []module.Module{
        tenants.Module{},
        billing.Module{},
        workflows.Module{},
    }
    var migrations []module.Migration
    migrations = append(migrations, tenants.Migrations()...)
    migrations = append(migrations, billing.Migrations()...)
    migrations = append(migrations, workflows.Migrations()...)
    return mods, migrations
}
```

Core modules and their migrations always appear first. Feature modules and their migrations follow in the order listed in `uses`.

## Migration Workflow

Migration generation is a separate workflow from service generation. It is triggered by schema changes, not annotation changes.

```bash
hestia migrate <module>
```

Runs `anansi schema migrate` against the module's schemas, producing migration files in each service's `model/migrations/` directory. The developer then implements the `Transformer` function only when data transformation is needed.

`hestia service generate` never touches migrations.

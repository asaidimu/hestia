# User Refactor Plan

Two coordinated changes:

- **A.** Move user registration out of `auth` and into the `users` feature as `system:users:user:create` — fixing the co-location problem where user creation lived under an authorization feature.
- **B.** Adopt the autogenerated `SystemUsers` singleton (`InitSystemUsersModel` / `SystemUsersModel()`) and drop the hand-rolled `NewSystemUsers` constructor, with a small reset helper to keep Reset and tests working.

---

## A. Move registration into `users` (`system:users:user:create`)

### Rationale

User creation is identity/user-management, not authorization. Today the `user`
resource is split:

| Resource | Message | Location |
|---|---|---|
| Create | `system:auth:user:register` | **auth** |
| Read | `system:users:user:get` / `query` | users |
| Update | `system:users:user:update` | users |
| Password | `system:users:password:change` | users |
| Delete | `system:users:user:delete` | users |

`auth` should handle sessions, credentials, and password reset only.

### Steps

1. **`core/internal/feature/users/schema/data_transfer_objects.go`**
   - Add `UserRegisterInput` — embeds `schema.UserRegister` (keeps its
     `input:"payload.*"` tags) so the projection is inherited flat.
   - Add `UserRegisterInputSchema()` accessor via
     `dispatch.SchemaFromTypeWithTag[UserRegisterInput]("input", true)`.

2. **`core/internal/feature/users/handler.go`**
   - Add `NewCreateUserHandler(users *schema.SystemUsers) abstract.MessageHandler`
     — the body of the current `auth.NewRegisterHandler`:
     `BindToTag(&input, "input")` → `users.Register(...)` →
     `Result{Document: user.MustDocument()}`.

3. **`core/internal/feature/users/feature.go`**
   - Register `system:users:user:create`:
     - `Handler: NewCreateUserHandler(deps.UserModel)`
     - `Intent: abstract.Create`
     - `Input: runtime.Input{Schema: schema.UserRegisterInputSchema(), Payload: definition.FieldTypeObject}`
     - `Output: schema.UserOutputSchema()`
     - `Description: "Create a new user"`

4. **`core/internal/feature/auth/feature.go`**
   - Remove the `system:auth:user:register` registration.

5. **`core/internal/feature/auth/handler.go`**
   - Remove `NewRegisterHandler`.

6. **`core/internal/feature/auth/schema.go`**
   - Remove `registerInputSchema()`.

7. **`core/internal/feature/auth/policies.go`**
   - Remove the `system:auth:user:register` binding.

8. **`core/internal/feature/users/policies.go`**
   - Add `{Name: "system:users:user:create", RuleKey: "administrator", Description: "Create new user"}`.

9. **`core/internal/feature/gen_features.go`** (line 55)
   - Move the registration rate-limit case from `"system:auth:user:register"`
     to `"system:users:user:create"`.

10. **`client/auth/store.ts`**
    - Move `register()` to a `client/users/` module
      (e.g. `client/users/store.ts`) dispatching `system:users:user:create`.

11. **`client/core/routes.gen.ts`**
    - Regenerate so the route becomes
      `POST /api/system/users/user/create`.

12. **`FRAMEWORK_GUIDE.md`**
    - Fix the message tables (lines ~428-435 and ~437-445): remove
      `system:auth:user:register` from the auth table, add
      `system:users:user:create` to the users table, drop the phantom
      `system:users:user:register` and `system:users:user:list` rows.
    - Fix the route-derivation table (lines ~728-731): the action segment is
      NOT dropped — `system:auth:session:create` →
      `POST /api/system/auth/session/create` and `system:users:user:get` →
      `GET /api/system/users/user/get/{user_id}`.

## B. Use the autogenerated `SystemUsers` singleton

### Rationale

`NewSystemUsers` duplicates the generated `InitSystemUsersModel` logic and
bypasses the singleton's locking/retry-safety. Use the generated singleton
instead, with a small reset helper to preserve the Reset lifecycle and test
isolation that the fresh constructor previously provided.

### Constraints

- `InitSystemUsersModel` is **idempotent** — it returns the existing singleton
  forever (codegen `generate.go:623-625`). Without a reset hook:
  - `Application.Reset` (boot/app.go:264) would keep the singleton pinned to a
    *closed* persistence → dead DB handle.
  - Tests creating a fresh `testutil.NewPersistence(t)` per test would leak the
    first test's persistence into all later tests.

### Steps

1. **`core/internal/feature/users/schema/system_user_utils.go`**
   - Delete `NewSystemUsers`.
   - Add `ResetSystemUsersModel()` — clears the generated package-level
     `systemUsersModel` var (must reset to `nil`, safe under
     `systemUsersModelMu`). Hand-written, lives alongside the domain methods.

2. **`core/internal/feature/provider.go`** (line 84)
   - Replace `schema.NewSystemUsers(ps.Persist, ps.Logger)` with
     `schema.InitSystemUsersModel(ps.Persist, ps.Logger)`.

3. **Reset lifecycle** (`core/internal/boot/app.go` or the Reset path)
   - Call `schema.ResetSystemUsersModel()` before re-running module `Setup`
     with the new persistence so the singleton re-binds to the fresh DB.

4. **Tests**
   - In `core/internal/feature/users/users_test.go`,
     `core/internal/feature/model_test.go`,
     `core/internal/feature/auth/auth_test.go`:
     - Replace `schema.NewSystemUsers(p, logger)` with
       `schema.InitSystemUsersModel(p, logger)`.
     - Call `schema.ResetSystemUsersModel()` (via `t.Cleanup`) so each test
       gets a fresh singleton bound to its own persistence.
